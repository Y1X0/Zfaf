## 1. نموذج الفاعلين

```
┌────────────────────────────────────────────────────────────────┐
│ Anonymous       بلا حساب — يفتح دعوة عامة، يرسل RSVP           │
│ Guest (tokened) رمز ضيف في الرابط ?g=xxx — تخصيص فقط (Phase 3)│
│ Customer        حساب مسجّل — ينشئ ويدير دعواته                 │
│ Planner         Customer بحدود أعلى + إدارة فريق (Phase 3)     │
│ Support         موظف — قراءة + إيقاف دعوة                      │
│ Admin           إدارة كاملة عدا الأسعار والأدوار               │
│ SuperAdmin      كل شيء + الأسعار + الأدوار                     │
│ System          مهام خلفية — يتجاوز التفويض بحدود صريحة         │
└────────────────────────────────────────────────────────────────┘
```

```typescript
type Actor =
  | { kind: 'anonymous'; ipHash: string }
  | { kind: 'guest'; invitationId: string; guestId: string }
  | { kind: 'user'; userId: string; role: UserRole; emailVerified: boolean;
      status: UserStatus; sessionId: string; memberships: Membership[] }
  | { kind: 'system'; jobName: string };
```

> **قرار مهم:** `Actor` نوع صريح لا `session | null`. هذا يجبر كل نقطة تفويض
> على التعامل مع كل الحالات، ويمنع الخطأ الكلاسيكي «نسينا حالة المجهول».

## 2. المصادقة

### 2.1 الجلسات — لماذا قاعدة البيانات لا JWT

| المتطلب | JWT | جلسات DB |
|---------|-----|----------|
| تسجيل خروج فوري من كل الأجهزة | ❌ مستحيل بلا قائمة إبطال (وهي DB على أي حال) | ✅ `UPDATE` واحد |
| إيقاف حساب مسيء فوراً | ❌ يظل الرمز صالحاً حتى انتهائه | ✅ فوري |
| تغيير الدور يسري فوراً | ❌ | ✅ |
| «أجهزتي النشطة» | ❌ | ✅ |
| قابلية التوسع | ✅ بلا حالة | جيدة (بحث بمفتاح + cache) |
| حجم الكوكي | كبير | 32 بايت |

**قرارنا:** جلسات قاعدة بيانات. حجّة «JWT أسرع» لا تنطبق علينا — الطلب سيلمس DB على أي حال.
والقدرة على الإبطال الفوري **متطلب تشغيلي حقيقي** (منصة يمكن إساءة استخدامها).

📄 [ADR-0006](adr/0006-database-sessions-not-jwt.md)

### 2.2 دورة حياة الجلسة

```
تسجيل الدخول
   │
   ├─ 1. توليد رمز عشوائي 32 بايت (CSPRNG)
   ├─ 2. تخزين sha256(token) في sessions  ← لا يُخزَّن الرمز الخام أبداً
   ├─ 3. ضبط الكوكي:
   │      __Host-zfaf_session=<base64url(token)>
   │      HttpOnly · Secure · SameSite=Lax · Path=/ · Max-Age=2592000
   └─ 4. تسجيل: user_agent, ip_hash, created_at

كل طلب
   ├─ استخراج الرمز → sha256 → بحث
   ├─ تحقق: غير منتهية، غير مبطلة، المستخدم نشط
   ├─ تمديد انزلاقي: إن مضى > يوم على last_used_at → تحديث + تمديد
   └─ حد أقصى مطلق: 90 يوماً من الإنشاء مهما حدث

خروج → revoked_at = now()
خروج من الكل / تغيير كلمة المرور → إبطال كل جلسات المستخدم
```

**بادئة `__Host-`:** تفرض `Secure` و`Path=/` وتمنع ضبطها من نطاق فرعي —
حماية إضافية مجانية ضد تثبيت الجلسة عبر نطاق فرعي مخترق.

### 2.3 كلمات المرور

```typescript
// argon2id — التوصية الحالية من OWASP
{ type: argon2.argon2id, memoryCost: 19456 /*19MiB*/, timeCost: 2, parallelism: 1 }
```

**السياسة:**
- الحد الأدنى **10 أحرف** — لا قواعد تعقيد إجبارية.
  (البحث الحديث: قواعد التعقيد تنتج `P@ssw0rd1!` — الطول أهم بكثير.)
- فحص مقابل قوائم كلمات المرور المسربة (k-anonymity عبر Have I Been Pwned).
- عرض قوة كلمة المرور، بلا رفض تعسفي.
- **لا انتهاء صلاحية دوري** (يدفع المستخدمين لأنماط ضعيفة).
- عند التغيير: إبطال كل الجلسات الأخرى + إشعار بريدي.

### 2.4 الحماية من التخمين

| الطبقة | القاعدة |
|--------|---------|
| لكل IP | 20 محاولة/ساعة عبر كل الحسابات |
| لكل حساب | 5 محاولات/15 دقيقة، ثم قفل تصاعدي (1د، 5د، 15د، 60د) |
| CAPTCHA | Turnstile بعد 3 محاولات فاشلة |
| زمن ثابت | **الرد يستغرق نفس الوقت** سواء وُجد البريد أم لا |
| الرسالة | «البريد أو كلمة المرور غير صحيحة» — لا تكشف أيهما |
| الإشعار | بريد عند تسجيل دخول من جهاز جديد |

### 2.5 تفعيل البريد

- رمز عشوائي 32 بايت، يُخزَّن مُجزّأً (hashed)، صلاحية 24 ساعة، **استخدام واحد**.
- **التسجيل لا يتطلب تفعيلاً** (لا نعرقل التجربة الأولى) — لكن **النشر يتطلبه**.
  هذا يوازن بين تقليل الاحتكاك ومنع الإساءة الجماعية.
- الرابط لا يسجّل الدخول تلقائياً (يمنع هجمات عبر روابط مسرّبة).

### 2.6 استعادة كلمة المرور

- رمز 32 بايت، مُجزّأ، صلاحية **15 دقيقة**، استخدام واحد.
- **الاستجابة دائماً 200** حتى لو البريد غير مسجّل — لا نكشف من له حساب.
- عند الاستخدام: إبطال كل الجلسات + بريد إشعار.
- حد معدل: 3/ساعة لكل بريد و لكل IP.

### 2.7 OAuth (Google)

- PKCE + `state` مربوط بالجلسة (مضاد CSRF).
- الربط بالبريد **فقط إن كان مُتحققاً من المزوّد** (`email_verified: true`).
  ⚠️ الربط الأعمى بالبريد ثغرة استيلاء معروفة.
- يجب أن يبقى للمستخدم طريقة دخول واحدة على الأقل (لا يمكن فصل آخر مزوّد بلا كلمة مرور).

### 2.8 المصادقة الثنائية (Phase 2)

- TOTP (RFC 6238) + رموز احتياطية (10 رموز، تُعرض مرة واحدة، مُجزّأة).
- **إلزامية لـ `admin` و `superadmin`** — لا استثناء.
- اختيارية للعملاء.

## 3. التفويض

### 3.1 النموذج

**RBAC (أدوار المنصة) + ReBAC (علاقة الملكية بالمورد).**

هذا التمييز مهم: دور «customer» لا يعني شيئاً بلا سؤال «هل هذه دعوته؟».
معظم قراراتنا علائقية لا دورية.

```typescript
interface Membership {
  invitationId: string;
  role: 'owner' | 'editor' | 'viewer';
}
```

### 3.2 مصفوفة الصلاحيات

| الإجراء | Anon | Guest | Owner | Editor | Viewer | Support | Admin | Super |
|---------|:----:|:-----:|:-----:|:------:|:------:|:-------:|:-----:|:-----:|
| عرض دعوة منشورة | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| إرسال RSVP | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

### 3.3 خصوصية بيانات الضيوف من الموظفين

قرار متعمّد: **حتى `superadmin` لا يستطيع تصفح أسماء وهواتف ضيوف دعوة ما.**

الأسباب:
- هؤلاء أطراف ثالثة لم يوافقوا على شيء ولا علاقة لهم بنا.
- لا يوجد سبب تشغيلي مشروع لتصفح قوائم المدعوين.
- تقليل سطح الضرر عند اختراق حساب موظف.

**ما يراه الموظفون:** أعداد مجمّعة فقط (عدد الردود، نسبة الحضور).

**الاستثناء الوحيد:** أمر قضائي أو تحقيق إساءة موثّق. عندها إجراء **كسر زجاج**:
موافقة شخصين + سبب مكتوب + تسجيل + إشعار للمالك. لا يتم بضغطة زر.

### 3.4 نقطة التنفيذ الوحيدة

```typescript
export function can(actor: Actor, action: Action, resource?: Resource): Decision
```

- كل مسار مُغيِّر أو قارئ لبيانات مملوكة يستدعيها.
- **`403` لا يُرجَع أبداً لموارد يملكها غيرك — يُرجَع `404`.**
  السبب: `403` يؤكد أن المورد موجود. هذا تسريب معلومات (enumeration).
- تُختبَر بمصفوفة كاملة: كل دور × كل إجراء × (مالك/عضو/غريب).

### 3.5 عزل المستأجرين

```
الطبقة 1 — المستودع:     كل استعلام يفرض owner_id/membership داخلياً
الطبقة 2 — التفويض:      can() قبل كل عملية
الطبقة 3 — RLS (Ph2):    سياسات Postgres كشبكة أمان
الطبقة 4 — الاختبارات:   مصفوفة IDOR آلية في CI
```

**اختبار العزل الإلزامي:** لكل نقطة نهاية تأخذ معرّف مورد:
مستخدم A ينشئ مورداً → مستخدم B يحاول الوصول بمعرّف A → **يجب أن يحصل على 404**.
مولَّد آلياً من قائمة المسارات، فلا يمكن نسيان نقطة جديدة.

## 4. رموز الضيوف (Phase 3)

```
https://zfaf.app/i/ahmad-sarah?g=K7M2P9X4R6T8V1W3
```

| الخاصية | القيمة |
|---------|--------|
| التوليد | CSPRNG، 16 حرفاً base32 (80 bit entropy) |
| التخزين | مُجزّأ في `guests.token_hash` |
| ما يمنحه | تحية بالاسم، عدد مقاعد مخصص، ملء مسبق |
| ما لا يمنحه | **لا وصول لأي بيانات إدارية أو ردود آخرين** |
| حد المعدل | 10 محاولات فاشلة/دقيقة لكل IP (ضد التخمين) |
| الإبطال | المالك يستطيع تدوير الرموز |

**اعتبارات:**
- ⚠️ الرابط سيُعاد توجيهه بين الضيوف عبر WhatsApp. **يجب ألا يحتوي على شيء ضار عند إعادة التوجيه** —
  أقصى ضرر: شخص آخر يرى «أهلاً خالد». مقبول.
- رمز غير صالح → يعمل كرابط عام عادي، بلا رسالة خطأ (تجربة أفضل، ولا كشف).
- `Referrer-Policy: no-referrer` على الصفحة لمنع تسريب الرمز إلى مواقع خارجية.

## 5. حماية CSRF

| الطبقة | الآلية |
|--------|--------|
| 1 | `SameSite=Lax` على كوكي الجلسة — يغطي الأغلبية |
| 2 | تحقق ترويسة `Origin` على كل الطلبات المُغيِّرة مقابل قائمة بيضاء |
| 3 | حماية Server Actions المدمجة في Next.js |
| 4 | رمز CSRF صريح للعمليات عالية المخاطر (تغيير البريد، حذف الحساب، الدفع) |
| 5 | إعادة إدخال كلمة المرور للعمليات الحساسة |

⚠️ **ملاحظة:** `SameSite=Lax` وحده لا يكفي. طلبات `GET` المُغيِّرة (وهي خطأ تصميمي أصلاً)
تمرّ معه. لذلك: **لا عملية مُغيِّرة عبر GET إطلاقاً.**

## 6. سجل التدقيق

يُسجَّل إلزامياً:

| الفئة | الأحداث |
|-------|---------|
| المصادقة | دخول (نجاح/فشل)، خروج، تغيير كلمة مرور، إعادة تعيين، تفعيل، ربط OAuth |
| الحساب | تغيير البريد، طلب الحذف، تغيير الدور، إيقاف/تفعيل |
| الدعوة | إنشاء، نشر، إلغاء نشر، تغيير slug، حذف، استرجاع |
| الإدارة | **كل** إجراء إداري بلا استثناء |
| الفوترة | دفع، استرداد، تغيير باقة، إلغاء |
| الأمان | تجاوز حد معدل، فشل تفويض، فشل تحقق توقيع webhook |

```typescript
interface AuditEntry {
  actorId?: string; actorType: string;
  action: string;                       // 'invitation.published'
  resourceType: string; resourceId: string;
  metadata: Record<string, unknown>;    // ⚠️ منقّى — لا أسرار ولا بيانات ضيوف
  ipHash?: string; requestId: string;
  createdAt: Date;
}
```

**قواعد:** غير قابل للتعديل أو الحذف · احتفاظ سنتان · **ممنوع تسجيل** كلمات المرور،
الرموز، أسرار الدفع، أو بيانات الضيوف الشخصية.

## 7. أمان حسابات الموظفين

- 2FA إلزامية.
- الجلسة الإدارية **4 ساعات فقط** (لا 30 يوماً).
- إعادة مصادقة للإجراءات الخطرة (إيقاف مستخدم، استرداد).
- قائمة IP بيضاء اختيارية (Phase 2).
- **مبدأ الأقل امتيازاً:** الافتراضي `support` لا `admin`. الترقية بموافقة صريحة.
- مراجعة ربع سنوية لقائمة من يملك أدواراً إدارية.
- بيئة الإدارة منفصلة المسار (`/admin`) بترويسات `no-store` صارمة و`X-Frame-Options: DENY`.

## 8. حذف الحساب

```
طلب الحذف
   │
   ├─ يوم 0    الحساب → pending_deletion · إبطال كل الجلسات
   │            كل الدعوات → PAUSED (الروابط تتوقف فوراً)
   │            بريد تأكيد فيه رابط تراجع
   │
   ├─ 0–30 يوماً   يمكن التراجع بتسجيل الدخول
   │
   └─ يوم 30   حذف صلب:
                • users, sessions, oauth_accounts
                • invitations + versions + events + rsvps
                • media_assets + الملفات في R2
                • analytics_events (مجهّلة أصلاً)
                ✔ يُحتفَظ به: سجلات الدفع (قيد محاسبي، بلا بيانات شخصية زائدة)
                              audit_logs (معرّف الفاعل → مجهّل)
```

**تنبيه مهم:** حذف الحساب يوقف الدعوات فوراً. لو كان العرس بعد يومين، تُفقد الدعوة للضيوف.
لذلك: تحذير صريح جداً في الواجهة + بريد تأكيد + نافذة التراجع.
