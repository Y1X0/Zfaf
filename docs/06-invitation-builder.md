# 06 — Invitation Builder & Preview

**الإصدار:** v0.1 · **الحالة:** Draft

> الـ Builder هو المكان الذي يُكسب فيه المنتج أو يُخسر. المستخدم غير تقني، على جواله غالباً،
> ولديه صبر محدود. الهدف: **من فارغ إلى منشور في أقل من 8 دقائق.**

---

## 1. مبادئ التصميم

1. **لا زر «حفظ».** الحفظ التلقائي هو السلوك الوحيد. زر الحفظ يعني: «قد تفقد عملك».
2. **الافتراضيات جميلة.** المستخدم الذي لا يغيّر شيئاً يجب أن يحصل على دعوة تصلح للنشر.
3. **الكشف التدريجي.** الخطوة تعرض 3–5 حقول لا 15. المتقدّم خلف «خيارات إضافية».
4. **المعاينة هي الحقيقة.** ما يراه = ما سيُنشر بالضبط (نفس الـ Renderer).
5. **يعمل على الجوال.** ~40% من المنشئين سيبنون دعوتهم من الجوال. ليست حالة هامشية.
6. **لا يُعاقَب على الاستكشاف.** كل شيء قابل للتراجع، ولا شيء يُنشر بلا تأكيد صريح.

## 3. الخطوات

| # | الخطوة | إجباري | حقول |
|---|--------|:------:|------|
| 0 | اختيار القالب | ✅ | 3 بطاقات بمعاينة فورية |
| 1 | العروسان | ✅ | اسم العريس، اسم العروس · *(اختياري: الاسم المختصر، رسالة، صورة)* |
| 2 | الموعد | ✅ | التاريخ، الوقت، المنطقة الزمنية · *(اختياري: وقت الانتهاء)* |
| 3 | المكان | ⚠️ | اسم القاعة، العنوان · *(اختياري: خريطة/إحداثيات)* |
| 4 | برنامج الحفل | ❌ | أحداث متعددة — يُتخطى بالكامل إن لم يُرد |
| 5 | الصور | ❌ | غلاف، صورة العروسين، معرض |
| 6 | الموسيقى | ❌ | من مكتبة المنصة |
| — | التصميم | ❌ | ألوان، خطوط، حركات (متاح دائماً من الشريط الجانبي) |
| — | الأقسام | ❌ | تفعيل/تعطيل/ترتيب (متاح دائماً) |

**الحد الأدنى الصالح للنشر:** اسم العريس + اسم العروس + التاريخ. **ثلاثة حقول فقط.**
كل ما عداها له افتراضي معقول أو يُخفى القسم تلقائياً إن كان فارغاً.

> **قرار UX مهم:** قسم فارغ لا يُعرض. مستخدم لم يرفع صوراً ⇒ قسم المعرض يختفي من الدعوة تلقائياً،
> ولا نُظهر له «لا توجد صور». هذا يجعل الافتراضيات تعمل بلا تدخل.

### ملاحظات على حقول حساسة

**المنطقة الزمنية:** تُكتشف تلقائياً من المتصفح مع عرضها بوضوح وإمكانية التغيير.
عرض تأكيدي دائماً: «الحفل الساعة ٨:٠٠ مساءً بتوقيت الرياض».

**الإحداثيات:** المستخدم العادي لا يعرف Latitude/Longitude. المدخل الفعلي هو:
لصق رابط Google Maps → نستخرج الإحداثيات منه. مع بديل: بحث بالاسم على خريطة مضمّنة.
حقول lat/lng الخام تبقى خلف «إدخال يدوي متقدم».

## 4. الحفظ التلقائي

### الآلية

```
تغيير في حقل
   │
   ├─▶ تحديث الحالة المحلية فوراً  →  المعاينة تتحدث (< 16ms، بلا شبكة)
   │
   └─▶ إضافة عملية JSON Patch إلى طابور معلّق
           │
           ├─ debounce 1500ms  (يُعاد ضبطه مع كل ضغطة مفتاح)
           ├─ أو فوراً عند: تغيير الخطوة، فقدان التركيز عن حقل مهم، إخفاء الصفحة
           │
           ▼
      PATCH /api/v1/invitations/{id}/document
           { baseVersion, patch: [...] }
           │
           ├─ 200 → المؤشر: «تم الحفظ ✓» + تحديث baseVersion
           ├─ 409 → معالجة التعارض (§4.3)
           └─ فشل شبكة → إعادة محاولة أسّية (1s, 2s, 4s, 8s) + المؤشر: «سيُحفظ عند عودة الاتصال»
```

**لا نرسل طلباً مع كل حرف.** الـ debounce + دمج الـ patches يعني: الكتابة المستمرة لمدة دقيقة
تنتج طلباً واحداً أو اثنين، لا ستين.

### مؤشر الحالة (مهم نفسياً)

| الحالة | العرض |
|--------|-------|
| نظيف | `✓ تم الحفظ` (رمادي، هادئ) |
| معلّق | `● جارٍ الحفظ…` |
| غير متصل | `⚠ غير متصل — تعديلاتك محفوظة محلياً` (أصفر) |
| فشل | `⚠ تعذّر الحفظ [إعادة المحاولة]` (أحمر) |

### الحماية من فقدان البيانات

```
1. مسودة محلية في IndexedDB بعد كل تغيير (فوري، بلا شبكة)
2. beforeunload يحذّر إن كان هناك معلّق
3. عند إعادة الفتح: إن كانت المسودة المحلية أحدث من الخادم
       → «لديك تعديلات غير محفوظة من [وقت]. استعادتها؟»
4. Service Worker يعيد المحاولة في الخلفية (Phase 2)
```

⚠️ **حالة الجوال الحرجة:** المستخدم يفتح تطبيق الصور لاختيار صورة → المتصفح يُنهى من الذاكرة
(شائع جداً على iOS). **يجب** أن تُستعاد كل التعديلات عند العودة. IndexedDB هو ما يضمن ذلك.

### 4.3 معالجة التعارض

نموذج بسيط ومبرَّر (لا CRDT):

```
409 من الخادم مع { currentVersion, currentDocument, conflictingPaths }
   │
   ├─ لا تقاطع بين مساراتي ومسارات التعارض
   │     → دمج تلقائي صامت، تحديث baseVersion، متابعة
   │
   └─ يوجد تقاطع
         → حوار: «فُتحت هذه الدعوة في مكان آخر»
            [إبقاء تعديلاتي] [استخدام النسخة الأخرى] [عرض الفرق]
```

**لماذا لا CRDT/OT؟** حالة الاستخدام الفعلية هي مستخدم واحد على جهاز أو جهازين، لا تحرير
تعاوني متزامن. التحرير المشترك يأتي في Phase 3 لحسابات المنظّمين، وحينها نراجع القرار بقياس حقيقي.

## 5. المعاينة الحية

### المعمارية

```
حالة الـ Builder (React)
        │
        │  نفس الـ document المستخدم في النشر
        ▼
  <InvitationRenderer document={draft} mode="preview" />
        │
        ├─ عرض داخل الصفحة (سطح المكتب/جوال، عبر container queries)
        └─ أو داخل <iframe> لعزل حقيقي   ← نستخدم iframe
```

**قرار: iframe.** السبب:
- عزل CSS كامل — أنماط الـ Builder لا تتسرب إلى الدعوة والعكس.
- محاكاة صادقة لأحجام الأجهزة (media queries تعمل على عرض الـ iframe الحقيقي).
- سلوك التمرير والحركات مطابق للصفحة العامة.

**التكلفة:** التواصل عبر `postMessage` وتحميل أولي أبطأ قليلاً.
**التخفيف:** الـ iframe يُحمَّل مرة واحدة؛ التحديثات تُرسَل كرسائل (patch) لا كإعادة تحميل.

```
Builder ──postMessage({type:'doc:update', patch})──▶ iframe
Builder ◀──postMessage({type:'preview:ready'})───── iframe
Builder ◀──postMessage({type:'section:click', id})── iframe   ← النقر على قسم يفتح إعداداته
```

### أوضاع العرض

| الوضع | العرض | ملاحظة |
|-------|-------|--------|
| 📱 جوال | 390×844 | **الافتراضي** — لأنه واقع الاستخدام |
| 💻 لوحي | 768×1024 | |
| 🖥 مكتب | 1280×800 | |
| ⛶ ملء الشاشة | كامل | معاينة نهائية قبل النشر |

**نقطة مهمة:** الافتراضي هو الجوال. هذا ليس تفصيلاً — إنه يذكّر المستخدم طوال الوقت
بالسياق الحقيقي الذي ستُشاهد فيه دعوته.

### الأداء

- تغيير الثيم (لون/خط) → تحديث CSS variable فقط، **بلا re-render** → فوري.
- تغيير المحتوى → re-render للقسم المتأثر فقط (`React.memo` بمقارنة على مستوى القسم).
- إعادة الترتيب → إعادة ترتيب DOM مع انتقال متحرك.

## 7. لوحة الأقسام

```
┌─ الأقسام ──────────────────────────┐
│ ⇅ الافتتاحية        [مقفل]  👁     │  ← required، لا يُعطَّل
│ ⇅ العروسان          ↑ ↓     👁     │
│ ⇅ العد التنازلي     ↑ ↓     👁     │
│ ⇅ برنامج الحفل      ↑ ↓     👁     │
│ ⇅ الموقع            ↑ ↓     👁     │
│ ⇅ المعرض            ↑ ↓     👁̶     │  ← مخفي (لا صور مرفوعة)
│ ⇅ تأكيد الحضور      ↑ ↓     👁     │
│ ⇅ الخاتمة           [مقفل]  👁     │
└────────────────────────────────────┘
```

**MVP: أزرار ↑↓** لا Drag & Drop. السبب:
- تعمل بلا عيوب على اللمس (D&D على الجوال صعب فعلاً).
- متاحة للوصولية (لوحة مفاتيح، قارئ شاشة) بلا عمل إضافي.
- ~4 ساعات عمل مقابل ~3 أيام للـ D&D اللمسي الصحيح.
- تعطي 90% من القيمة.

Drag & Drop في Phase 2 عبر `dnd-kit` (يدعم اللمس والوصولية) — البيانات لا تتغير إطلاقاً،
فقط الواجهة. لذلك التأجيل بلا دَين تقني.

## 8. تدفق النشر

```
[نشر]
   │
   ├─ 1. فحص الاكتمال
   │      ✓ الأسماء والتاريخ موجودة
   │      ⚠ لم تختر مكاناً — «انشر بدون مكان؟» (تحذير لا حظر)
   │
   ├─ 2. اختيار الرابط
   │      zfaf.app/i/[ ahmad-sarah        ]  ✓ متاح
   │      (مقترح تلقائياً من الأسماء، قابل للتعديل، فحص فوري)
   │
   ├─ 3. تأكيد بريدي (إن لم يكن مفعّلاً)
   │
   ├─ 4. فحص الباقة (Phase 2 → صفحة الدفع)
   │
   ├─ 5. مراجعة أخيرة
   │      «تأكد من التاريخ والوقت — سيراها ضيوفك»
   │      [عرض الدعوة كما سيراها ضيوفك]
   │
   └─ 6. 🎉 نُشرت
          ┌──────────────────────────────────────┐
          │  دعوتك جاهزة!                        │
          │  zfaf.app/i/ahmad-sarah   [نسخ]      │
          │                                      │
          │  [📱 مشاركة على واتساب]              │
          │  [⬇ تحميل QR]  [👁 عرض الدعوة]      │
          └──────────────────────────────────────┘
```

### التعديل بعد النشر

```
دعوة منشورة → المستخدم يعدّل
   │
   ├─ التعديل يذهب للمسودة فقط
   ├─ شريط دائم: «لديك تعديلات غير منشورة  [معاينة] [نشر التحديث]»
   └─ الدعوة العامة تظل على النسخة السابقة حتى النشر الصريح
```

**هذا يمنع أسوأ سيناريو:** مستخدم يفتح دعوته ليصلح خطأً مطبعياً، فيرى 200 ضيف دعوة نصف مكتملة.

## 10. معالجة الأخطاء

| الحالة | السلوك |
|--------|--------|
| فشل رفع صورة | خطأ على مستوى الصورة، لا يعطّل الخطوة، مع [إعادة المحاولة] |
| فقدان الاتصال | لافتة، حفظ محلي، إعادة محاولة تلقائية عند العودة |
| انتهاء الجلسة | حوار «سجّل الدخول للمتابعة» — **بلا فقدان أي تعديل** |
| تجاوز حد الباقة | رسالة واضحة + ما الذي يفتحه الترقية (بلا إلحاح) |
| قسم مكسور في المعاينة | تدهور رشيق: نص «تعذّر عرض هذا القسم» + تقرير آلي |
| صورة كبيرة جداً | ضغط تلقائي في المتصفح قبل الرفع + إعلام بما حدث |

## 11. معمارية الحالة في الواجهة

```typescript
// حالة محلية بـ reducer — لا مخزن عام
type BuilderState = {
  document: InvitationDocument;    // مصدر الحقيقة المحلي
  baseVersion: number;
  saveStatus: 'clean' | 'pending' | 'saving' | 'error' | 'offline';
  pendingPatches: JsonPatch[];
  history: { past: JsonPatch[][]; future: JsonPatch[][] };  // Undo/Redo
  activeStep: StepId;
  validation: Record<string, ValidationIssue[]>;
};
```

- **حالة الخادم** (القوالب، الموسيقى، الوسائط) عبر **TanStack Query**.
- **حالة المستند** محلية بـ `useReducer` — لأن كل تحديث يجب أن يكون فورياً وقابلاً للتراجع.
- **لا Redux/Zustand عام** — لا حاجة، ولا نضيف تعقيداً بلا مقابل.

## 12. الأداء

| المقياس | الهدف |
|---------|-------|
| تحميل الـ Builder (بارد) | ≤ 2.5s LCP |
| زمن ظهور أثر التعديل في المعاينة | ≤ 100ms |
| تحديث الثيم | ≤ 16ms (إطار واحد) |
| زمن استجابة Autosave (p95) | ≤ 400ms |
| JS الأولي للـ Builder | ≤ 250KB gzip |

**تقنيات:** تحميل كسول للوحات (التصميم/الأقسام) · تحميل مسبق لقالب المعاينة عند اختيار القالب ·
ضغط الصور في المتصفح قبل الرفع (يوفّر وقتاً وعرض نطاق).
