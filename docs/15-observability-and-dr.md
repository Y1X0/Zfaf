## 1. مبدأ المراقبة

> نراقب لنجيب على أسئلة، لا لنجمع بيانات.

الأسئلة التي يجب أن نجيب عليها خلال دقيقتين:
1. هل الموقع يعمل؟
2. هل الدعوات المنشورة تُعرض؟
3. هل RSVP يعمل؟
4. هل الدفع يعمل؟
5. لماذا يشتكي هذا المستخدم؟
6. هل تدهور شيء بعد آخر نشر؟

كل ما لا يخدم هذه الأسئلة = ضوضاء وتكلفة.

## 2. التسجيل المنظم

```typescript
logger.info('invitation.published', {
  requestId: ctx.requestId,
  userId: actor.userId,
  invitationId, templateKey, versionNumber,
  durationMs: 342,
});
```

### الحقول القياسية في كل سطر
`timestamp` · `level` · `event` · `requestId` · `service` · `env` · `version` · `durationMs`

### ⛔ ممنوع تسجيله — قائمة قاطعة

```
❌ كلمات المرور (حتى المُجزّأة)      ❌ رموز الجلسات
❌ رموز التفعيل/الاستعادة            ❌ بيانات البطاقات
❌ مفاتيح API والأسرار               ❌ أسماء الضيوف أو هواتفهم
❌ عناوين IP خام                     ❌ محتوى الدعوة (نصوص المستخدم)
❌ عناوين البريد الكاملة (نُجزّئها أو نقصّها)
```

**تنقية آلية:** طبقة redaction في المسجّل تحجب المفاتيح المعروفة قبل الكتابة —
لا نعتمد على انضباط المطورين وحده. وتُختبَر بوحدة اختبار.

### المستويات

| المستوى | الاستخدام |
|---------|-----------|
| `error` | تحتاج تدخلاً بشرياً |
| `warn` | شذوذ يستحق النظر (حد معدل، فشل تفويض) |
| `info` | أحداث أعمال (نشر، RSVP، دفع) |
| `debug` | التطوير فقط، مُعطَّل في الإنتاج |

**التجميع:** Axiom (أو Better Stack) · احتفاظ 30 يوماً · بحث بـ `requestId` أو `userId`.

## 3. تتبع الأخطاء

**Sentry** للواجهة والخادم والـ worker.

```typescript
Sentry.init({
  dsn: env.SENTRY_DSN,
  environment: env.NODE_ENV,
  release: env.APP_VERSION,
  tracesSampleRate: 0.1,
  beforeSend(event) {
    return scrubSensitive(event);       // ⚠️ إلزامي
  },
});
```

- **تنقية إلزامية** قبل الإرسال: بيانات المستخدم، محتوى الدعوة، بيانات الضيوف.
- Source maps مرفوعة وخاصة.
- الأخطاء مرتبطة بالإصدار → «هل بدأ هذا بعد نشرة اليوم؟» يُجاب فوراً.
- عتبة تنبيه: خطأ جديد يظهر > 10 مرات/5 دقائق.

|---------|-----------|

### مقاييس البنية
اتصالات DB · زمن الاستعلامات p95 · عمق الطابور · زمن انتظار المهام · نسبة إصابة الـ cache

### مؤشرات ويب حقيقية (RUM)

```typescript
// جمع خفيف جداً وبلا كوكيز — من مستخدمين حقيقيين على أجهزة حقيقية
```

والشبكات في المنطقة متفاوتة. RUM هو ما يخبرنا بالحقيقة.

## 5. التنبيهات

**مبدأ: التنبيه يوقظ إنساناً ⇒ يجب أن يكون قابلاً للتصرف.**
التنبيهات الكاذبة تُدرِّب الفريق على تجاهل التنبيهات — وهذا أخطر من عدم وجودها.

### P0 — يوقظ (على مدار الساعة)

| التنبيه | الشرط |
|---------|-------|
| الموقع ساقط | فحص الصحة يفشل مرتين متتاليتين |
| **الدعوات العامة لا تُعرض** | معدل خطأ `/i/*` > 5% لـ 3 دقائق |
| قاعدة البيانات غير متاحة | فشل الاتصال |
| معدل الأخطاء الحاد | 5xx > 5% لـ 5 دقائق |
| فشل النشر | `publish.success_rate` < 90% لـ 10 دقائق |
| اشتباه اختراق | تصعيد صلاحيات، وصول غير معتاد للأسرار |

### P1 — يُنبَّه (ساعات العمل)

RSVP يفشل > 10% · رفع الوسائط يفشل > 20% · طابور المهام > 1000 · الدفع يفشل > 10%
· LCP p75 > 3s · القرص > 80% · نسبة webhooks الفاشلة > 5%

### P2 — لوحة فقط
شذوذ التكلفة · تدهور بطيء في الأداء · ارتفاع حد المعدل · نمو التخزين

**قواعد:** كل تنبيه له runbook · تجميع لتجنّب العواصف · فترة صمت بعد الإقرار
· **مراجعة شهرية: كل تنبيه لم يؤدِّ لإجراء يُحذف أو يُعدَّل.**

## 7. معرّفات الطلبات والتتبع

```
الطلب → توليد requestId (UUIDv7) إن لم يوجد
      → يُمرَّر عبر AsyncLocalStorage
      → في كل سطر سجل
      → في كل استجابة (X-Request-Id) وفي جسم الخطأ
      → إلى الـ worker عبر بيانات المهمة
```

**القيمة العملية:** مستخدم يشتكي ويرسل لقطة تحوي `requestId` ⇒ نجد كل ما حدث خلال ثوانٍ.
بلا ذلك، تحقيق شكوى واحدة قد يستغرق ساعة.

**التتبع الموزّع (OpenTelemetry):** Phase 2 — عند تعدد الخدمات.

## 9. التعافي من الكوارث

### الأهداف

| السيناريو | RPO (فقد بيانات مقبول) | RTO (زمن التعافي) |
|-----------|:----------------------:|:------------------:|
| فشل تطبيق | 0 | 5 دقائق |
| تلف قاعدة البيانات | 5 دقائق (PITR) | 2 ساعة |
| فقد كامل لقاعدة البيانات | 24 ساعة (آخر نسخة) | 4 ساعات |
| فقد الوسائط | 7 أيام | 8 ساعات |
| فشل منطقة كاملة | 24 ساعة | 8 ساعات |
| حذف عرضي (خطأ بشري) | 5 دقائق | 1 ساعة |

**تبرير الأرقام:** الدعوات المنشورة **تظل تُخدَم من CDN** (`stale-while-revalidate=86400`)
حتى أثناء انقطاع كامل لقاعدة البيانات. لذلك RTO يقاس بأثره على **الكتابة** لا على **القراءة**.
الضيف الذي يفتح دعوة أثناء العطل يراها طبيعية. هذا قرار معماري مقصود، وهو ما يجعل RTO
البالغ 4 ساعات مقبولاً تجارياً.

### إجراء التعافي

```
1. اكتشاف        (تنبيه آلي أو بلاغ)
2. تقييم          نطاق الضرر؟ فقد بيانات؟ منذ متى؟
3. احتواء         منع تفاقم الضرر (وضع صيانة إن لزم)
4. إعلان          صفحة الحالة + إشعار المستخدمين إن > 15 دقيقة
5. تعافٍ          استرجاع من نسخة / PITR / تحويل
6. تحقق           فحوص سلامة، اختبارات دخانية، تأكيد أعداد
7. استئناف        إعادة الحركة تدريجياً
8. تواصل          إشعار الحل
9. مراجعة         تحليل بلا لوم خلال 48 ساعة
```

### تمرين DR

**تمرين كامل كل ربع سنة** على staging:
استرجاع من نسخة، محاكاة فقد منطقة، اختبار التراجع، تنفيذ runbook والتحقق من دقته.
**نقيس RTO الفعلي ونقارنه بالهدف.** فجوة ⇒ إما نُصلح الإجراء أو نُصحّح الهدف.

## 13. أتمتة التكلفة

```
مراقبة يومية للتكلفة → تنبيه عند تجاوز العتبة
   ├─ ارتفاع مفاجئ في عرض النطاق  → فحص إساءة استخدام أو ارتباط دعوة بموقع كبير
   ├─ ارتفاع في التخزين           → فحص حسابات إساءة الاستخدام
   ├─ ارتفاع في حوسبة DB          → فحص استعلامات بطيئة جديدة
   └─ ارتفاع في البريد            → فحص حلقة إرسال أو إساءة
```

**سيناريو حقيقي متوقّع:** دعوة تُشارَك في مجموعة واتساب كبيرة أو تنتشر → آلاف الزيارات
خلال دقائق. CDN يمتصها. لكن **إن كانت الصور غير محسّنة، ينفجر عرض النطاق.**
لهذا تحسين الصور بند تكلفة لا بند أداء فقط.
