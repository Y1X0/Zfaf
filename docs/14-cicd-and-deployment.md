# 14 — CI/CD & Deployment Architecture

**الإصدار:** v0.1 · **الحالة:** Draft

---

## 1. البيئات

| البيئة | النطاق | قاعدة البيانات | النشر | البيانات |
|--------|--------|-----------------|-------|----------|
| **local** | localhost:3000 | Docker Compose | يدوي | مولّدة |
| **preview** | `pr-{n}.preview.zfaf.app` | فرع Neon لكل PR | آلي على كل PR | بذور اختبار |
| **staging** | `staging.zfaf.app` | Neon مخصصة | آلي على merge إلى `main` | مجهّلة |
| **production** | `zfaf.app` | Neon إنتاج | يدوي (زر) بعد staging | حقيقي |

**قواعد صارمة:**
- ممنوع الوصول إلى بيانات الإنتاج من أي بيئة أخرى — على مستوى الشبكة والأسرار.
- أسرار منفصلة تماماً لكل بيئة. لا مفتاح مشترك واحد.
- staging يستخدم مفاتيح دفع اختبارية فقط، ويتحقق من ذلك عند الإقلاع.
- بيانات الإنتاج لا تُنسخ إلى staging إلا بعد **تجهيل كامل** (أسماء، هواتف، بريد، صور).

## 2. التطوير المحلي

```yaml
# docker-compose.yml
services:
  postgres: { image: postgres:16-alpine, ports: ["5432:5432"] }
  redis:    { image: redis:7-alpine,     ports: ["6379:6379"] }
  minio:    { image: minio/minio,        ports: ["9000:9000"] }   # R2 محلياً
  mailpit:  { image: axllent/mailpit,    ports: ["8025:8025"] }   # التقاط البريد
```

```bash
pnpm install
pnpm db:up          # تشغيل الخدمات
pnpm db:migrate     # تطبيق الـ migrations
pnpm db:seed        # مستخدمون وقوالب ودعوات تجريبية
pnpm dev            # web + worker بالتوازي
```

**الهدف: من `git clone` إلى تطبيق يعمل في أقل من 10 دقائق.**
كل احتكاك هنا يتضاعف عبر كل عضو في الفريق وكل يوم.

```
     ┌───────────────────────────────────────────┐
     │  المرحلة 2 — اختبارات (بالتوازي، ~6د)     │
     │  • unit  • integration (Testcontainers)   │

     │  • build                                  │

                          ▼
     ┌───────────────────────────────────────────┐
     │  المرحلة 3 — نشر معاينة (~2د)             │
     │  • فرع DB جديد  • migrate  • seed  • نشر  │
     └────────────────────┬──────────────────────┘
                          ▼
     ┌───────────────────────────────────────────┐
     │  المرحلة 4 — فحوص على المعاينة (~4د)      │

     │  • لقطات بصرية  • Lighthouse  • axe       │
     └────────────────────┬──────────────────────┘

     ┌───────────────────────────────────────────┐

     │  • npm audit  • Trivy  • CodeQL           │
     └────────────────────┬──────────────────────┘
                          ▼
              كل الفحوص الإلزامية خضراء
```

### الفحوص الإلزامية (تمنع الدمج)

```
✅ lint · format · typecheck · module-boundaries
✅ unit · integration · migrations · security-matrix
✅ e2e-chromium · e2e-webkit
✅ visual-regression · lighthouse · a11y
✅ gitleaks · dependency-audit (Critical/High)
✅ build
```

### تحسينات السرعة
`turbo` مع تخزين مؤقت بعيد · تنفيذ متأثر فقط (`--filter=...[origin/main]`)
· تقسيم E2E على 4 عمّال · تخزين مؤقت لمتصفحات Playwright.

**الميزانية: < 12 دقيقة للفحوص الإلزامية.**

## 4. خط النشر

```
merge إلى main
   │
   ├─▶ نشر تلقائي إلى staging
   │      ├─ migrations (expand فقط)
   │      ├─ نشر web + worker
   │      ├─ فحص صحة
   │      └─ E2E دخاني على staging
   │
   ├─▶ ⏸ بوابة يدوية — موافقة بشرية
   │
   └─▶ نشر الإنتاج
          ├─ 1. migrations (expand فقط، متوافقة للخلف)
          ├─ 2. نشر worker أولاً    ← يجب أن يفهم الشكلين
          ├─ 3. نشر web            ← تبديل تدريجي
          ├─ 4. فحص صحة + مراقبة 10 دقائق
          ├─ 5. E2E دخاني على الإنتاج
          └─ 6. عند الفشل → تراجع تلقائي
```

**النشر بلا توقف:** إصداران يعملان معاً أثناء التبديل ⇒ **كل تغيير DB يجب أن يكون
متوافقاً مع الإصدارين**. هذا يفرض نمط expand/contract.

## 5. الـ Migrations في الإنتاج

### النمط الإلزامي

```
الإصدار N     — EXPAND: إضافة عمود nullable / جدول جديد. الكود القديم يعمل.
الإصدار N+1   — الكود يكتب في القديم والجديد.
(مهمة خلفية) — BACKFILL على دفعات.
الإصدار N+2   — الكود يقرأ من الجديد فقط.
الإصدار N+3   — CONTRACT: حذف القديم.
```

### القواعد

| القاعدة | السبب |
|---------|-------|
| ❌ لا `DROP`/`RENAME` في نفس نشرة الكود المستخدِم | يكسر الإصدار القديم أثناء التبديل |
| ✅ `CREATE INDEX CONCURRENTLY` | لا يقفل الجدول |
| ✅ `NOT NULL` بخطوتين (default → backfill → قيد) | تجنّب مسح كامل قافل |
| ✅ Backfill على دفعات (1000 صف، بفواصل) | لا يضغط على DB الحية |
| ⏱ migration > 5 ثوانٍ على staging | **يُرفض** ويُعاد تصميمه |
| 🔒 اختبار من صفر ومن نسخة الإنتاج | كل PR |
| 📋 مسار تراجع موثّق | لكل migration |

⚠️ **حالة خطرة:** `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT` على جدول كبير
قد يقفل الجدول في إصدارات Postgres الأقدم. نتحقق دائماً على نسخة بحجم الإنتاج.

## 6. التراجع (Rollback)

| النوع | الآلية | الزمن |
|-------|--------|-------|
| كود | إعادة النشر الفوري للإصدار السابق | < 2 دقيقة |
| كود (يدوي) | `git revert` + نشر | < 10 دقائق |
| Migration | مسار تراجع، أو استرجاع من PITR | متغيّر |
| بيانات | استرجاع PITR إلى نقطة زمنية | 30–60 دقيقة |
| علم ميزة | تعطيل فوري بلا نشر | < 30 ثانية |

**مبدأ:** كل تغيير محفوف بالمخاطر يوضع خلف **علم ميزة**. التراجع بتبديل علم أسرع
وأقل خطراً بكثير من التراجع بنشر.

```typescript
const flags = {
  'payments.enabled':          { default: false, env: ['staging'] },
  'templates.floral':          { default: false, rollout: 0.1 },
  'builder.dragAndDrop':       { default: false, users: ['beta'] },
```

مخزّنة في `settings` (JSONB) + مؤقتة في Redis · تُقيَّم server-side ·
تدعم النسبة المئوية وقوائم المستخدمين · تُدقَّق التغييرات في `audit_logs`.

**فائدة عملية:** فصل **النشر** عن **الإطلاق**. الكود يصل الإنتاج مبكراً ويُفعَّل حين نجهز.

## 8. طوبولوجيا الإنتاج

> **⚠️ عُدِّلت في بوابة الإطلاق الثانية — [ADR-0022](adr/0022-render-deployment-topology.md).**
> ما يلي هو التصميم كما كُتب في Phase 0: أربعة مزوّدين (Vercel · Neon · Upstash ·
> Fly.io). القرار الساري هو **Render** للتطبيق والعامل وPostgres وKey Value، مع
> بقاء Cloudflare (DNS · CDN · TLS) وR2 وResend كما هما. يُبقى المخطّط القديم هنا
> لأن سبب استبعاده جزء من القرار، لا لأنه ما زال ساري المفعول.
> التزويد نفسه لم يحدث؛ ما يصفه [`render.yaml`](../render.yaml) **مخطّط للمراجعة**،
> وخطواته في [docs/22](22-deployment-render.md).

```
                    ┌─────────────────────┐
                    │   Cloudflare        │
                    │   DNS · CDN · WAF   │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
     ┌─────────────┐   ┌──────────────┐  ┌──────────────┐
     │  Vercel     │   │  R2 Bucket   │  │ Cloudflare   │
     │  apps/web   │   │  (media)     │  │ Worker       │
     │             │   │              │  │ (media proxy)│
     └──────┬──────┘   └──────────────┘  └──────────────┘
            │
    ┌───────┼────────────────┬──────────────┐
    ▼       ▼                ▼              ▼
┌────────┐ ┌──────────┐ ┌─────────┐  ┌──────────────┐
│ Neon   │ │ Upstash  │ │ Resend  │  │  Fly.io      │
│Postgres│ │  Redis   │ │  Email  │  │ apps/worker  │
└────────┘ └──────────┘ └─────────┘  └──────┬───────┘
                                             │
                                    ┌────────▼────────┐
                                    │  Neon + R2      │
                                    └─────────────────┘
```

**المناطق:** أقرب منطقة للسوق المستهدف (الشرق الأوسط / أوروبا).
CDN عالمي يخدم الصفحات المخزّنة من الحافة، لذلك المسافة إلى الأصل تؤثر فقط على cache miss.

## 9. المجالات و DNS

```
zfaf.app             → Vercel (التطبيق)
www.zfaf.app         → 301 إلى zfaf.app
cdn.zfaf.app         → Cloudflare Worker → R2
staging.zfaf.app     → Vercel (staging)
*.preview.zfaf.app   → Vercel (المعاينات)
```

**البريد:** SPF + DKIM + DMARC (`p=quarantine` ثم `p=reject` بعد المراقبة).
⚠️ إعداد ناقص هنا يعني وصول بريد التفعيل إلى مجلد الرسائل غير المرغوبة — وتعطّل تدفق النشر بالكامل.

**النطاقات المخصصة (Phase 3):**
```
عميل: invite.example.com  →  CNAME  →  custom.zfaf.app
   1. المستخدم يضيف السجل   2. نتحقق عبر رمز TXT
   3. شهادة SSL آلية (Cloudflare for SaaS)   4. توجيه حسب ترويسة Host
```

## 10. الأسرار

| البيئة | المدير |
|--------|--------|
| local | `.env.local` (مستثنى من Git) |
| preview/staging/prod | متغيرات بيئة المنصة — مجموعتا `zfaf-config` و`zfaf-secrets` على Render ([ADR-0022](adr/0022-render-deployment-topology.md)) |
| CI | GitHub Actions Secrets |

**السياسات:**
- تدوير سنوي مجدول، وفوري عند أي اشتباه.
- ❌ **ممنوع** طباعة أي سر في سجل. أي سر يظهر في سجل = حادث ⇒ تدوير فوري.
- `gitleaks` على PRs **وعلى تاريخ المستودع بالكامل**.
- `.env.example` بقيم وهمية فقط، ملتزم في Git.
- تحقق مخطط البيئة عند الإقلاع → الفشل السريع أفضل من عطل غامض لاحقاً.

## 11. فحوص الصحة

```
GET /api/health          → { status:'ok', version, uptime }        (سطحي، للموازن)
GET /api/health/deep     → { db, redis, storage, mail }            (محمي)
GET /api/health/ready    → جاهزية القبول                            (للنشر)
```

`/api/health/deep` يفحص التبعيات فعلاً — لكنه محمي ومحدود المعدل
(كشف حالة البنية للعامة معلومة مفيدة للمهاجم).

> نفسها لم تتغيّر، وما تغيّر هو الجهة التي تُصدرها.

**خطة الهجرة موثّقة مسبقاً** ([16-cost-estimate.md](16-cost-estimate.md)) — لا نكتشف

## 15. قائمة تحقق الإطلاق

```
البنية
□ نطاقات الإنتاج مُعدّة، SSL نشط، HSTS preload مُقدَّم
□ SPF/DKIM/DMARC مُعدّة ومُختبَرة بإرسال حقيقي
□ النسخ الاحتياطي مفعّل ومُختبَر باسترجاع فعلي
□ المراقبة والتنبيهات تصل فعلاً إلى شخص
□ حدود التكلفة وتنبيهاتها مضبوطة

الأمان
□ كل بنود قائمة 12-security-threat-model §11
□ اختبار اختراق مكتمل والنتائج معالجة

المنتج
□ 3 قوالب مصقولة ومُختبَرة على أجهزة حقيقية
□ الاختبار اليدوي على iPhone و Android مكتمل
□ الشروط وسياسة الخصوصية منشورتان بلغتين
□ آلية البلاغ وإيقاف الدعوة مُختبَرتان
□ قناة دعم تعمل

التشغيل
□ Runbooks مكتوبة و**مُختبَرة**
□ الفريق يعرف من يُستدعى ومتى
□ خطة التراجع مُختبَرة على staging
```
