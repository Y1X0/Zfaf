# ADR-0004 — Template = JSON Manifest مُتحقَّق بـ Zod (لا React لكل قالب)

**الحالة:** ✅ Accepted · **اقتُرح:** 2026-08-16 · **اعتُمد:** 2026-08-16

## السياق

المتطلب صريح: *«لا تجعل إضافة Template جديد تحتاج تعديل عشرات الملفات»* و
*«صمّم Schema قابلاً للترجمة إلى UI»*.

النهج البديهي — كل قالب مكوّن React مستقل — ينتج حتماً:
- 70% كود مكرر بين القوالب.
- إصلاح خطأ في العد التنازلي = تعديل 7 ملفات (وستنسى واحداً).
- إضافة قسم جديد = تعديل كل القوالب.
- استحالة أن يخلط المستخدم بين أساليب القوالب.
- استحالة أن يضيف غير المبرمج قالباً.
- استحالة سوق قوالب آمن (Phase 3).

## القرار

**فصل رباعي:**

```
Manifest (JSON)   ← البنية والأسلوب الافتراضي   — يملكه المصمم/الأدمن
Document (JSON)   ← تخصيص المستخدم              — يملكه المستخدم
Registry (كود)    ← القدرات البصرية المتاحة     — يملكه المهندس
Renderer (كود)    ← دالة خالصة تجمعها          — يملكه المهندس
```

- الـ Manifest يُتحقَّق منه بـ **Zod**، ويُخزَّن في `template_versions.manifest` (JSONB).
- الـ Registry يربط `(type, variant)` بمكوّن React + `propsSchema` + تعريف محرر.
- الثيم يُحوَّل إلى **CSS Custom Properties** تُحقن inline — صفر JS للأسلوب.
- **الـ Manifest بيانات، لا كود.** لا `eval`، لا تعبيرات، لا JS مضمّن. أبداً.

## البدائل المرفوضة

| البديل | لماذا رُفض |
|--------|------------|
| مكوّن React لكل قالب | التكرار والصيانة والقيود المذكورة أعلاه |
| لغة قوالب (Handlebars/Liquid) | تفقد فوائد React (RSC، a11y، الأنواع)، وتضيف محرك تنفيذ = سطح هجوم |
| Headless CMS خارجي | تبعية خارجية على المسار الحرج، وتكلفة، وقيود على الأداء |
| قوالب تولّد كوداً وقت البناء | إضافة قالب تحتاج نشر إصدار — يناقض المتطلب مباشرة |

## العواقب

### إيجابية
- **قالب جديد = manifest + أصول** (< ساعتين، بلا نشر كود) في الحالة الشائعة.
- إصلاح خطأ في variant يفيد **كل القوالب** فوراً.
- إصدار نسخ القوالب مع تثبيت الدعوات المنشورة يصبح ممكناً.
- سوق القوالب (Phase 3) ممكن أمنياً — لأن المصمم الخارجي لا يستطيع تنفيذ كود.
- المستخدم يخلط: تخطيط قالب + أسلوب معرض آخر.

### سلبية
- **استثمار أولي أكبر** (~3 أسابيع لبناء المحرك قبل ظهور أول قالب).
- تجريد إضافي: تصحيح خطأ يمرّ عبر manifest → registry → renderer.
- **تخطيط بصري جديد فعلاً يحتاج variant جديداً في الكود** — لا وعد بالسحر.
  لكن الفرق جوهري: الـ variant **قدرة عامة** تُتاح لكل القوالب، لا نسخة لقالب واحد.

## اختبار الصحة (Falsifiable)

بنينا **ثلاثة قوالب مختلفة جذرياً** في MVP لهذا السبب بالذات.

> **المعيار:** إن احتاج القالب الثالث تعديلاً في `InvitationRenderer`، فالتصميم به خلل
> **ويُصلَح فوراً في Phase 1** لا لاحقاً.

**قياس مستمر:** نسبة القوالب الجديدة التي احتاجت كوداً. الهدف بعد Phase 2: ≤ 25%.

## الأمان

- ❌ لا `dangerouslySetInnerHTML` في أي مكوّن قسم (قاعدة ESLint تفشل CI).
- ✅ قيم الثيم تمرّ بـ allowlist أنماط صارمة قبل الحقن في CSS (منع حقن CSS).
- ✅ حدود حجم: ≤ 30 قسماً، مستند ≤ 256KB.
- ✅ `mapsUrl` مقيّد بنطاقات مسموحة.
