# ADR-0020 — الصفحة العامة بلا Hydration

**الحالة:** 🟡 Proposed — **تحتاج مصادقة صريحة من المالك** · **التاريخ:** 2026-08-16
**يمسّ:** [ADR-0002](0002-nextjs-fullstack-over-separate-api.md) · [ADR-0004](0004-json-template-manifest.md) · [ADR-0005](0005-published-snapshot-versioning.md)
**المصدر:** تعارض حقيقي اكتُشف في M6 بين ميزانية أداء معتمدة وأرضية إطار العمل

## السياق

ميزانية الأداء للصفحة العامة `/i/{slug}` **معتمدة من المالك** في
[PRD §4.1](../00-product-requirements.md) و[docs/07 §10](../07-frontend-architecture.md):

```
JS المُرسَل (gzip, initial) ≤ 90KB    (حد أقصى مطلق 120KB)
CSS (gzip, initial)        ≤ 25KB
```

عند قياس البناء الفعلي في M6 — قبل كتابة سطر واحد من كود الصفحة العامة —
تبيّن أن **أرضية App Router في Next 15.5 / React 19 هي 100.0 KB gzip** لأي مسار،
حتى مسار لا يحتوي على أي Client Component إطلاقاً:

```
static/chunks/af3f158d-*.js    53.0 KB gzip   (react-dom client runtime)
static/chunks/560-*.js         45.0 KB gzip   (next app-router client runtime)
static/chunks/webpack-*.js      1.6 KB gzip
main-app + page                 0.3 KB gzip
                              ─────────────
                              100.0 KB gzip
```

قياساً بالأداة نفسها التي أقرّها المالك في M5 (`scripts/measure-bundles.mjs`،
تضغط قطع المسار بنفسها ولا تثق بملصق Next).

**النتيجة:** الميزانية المعتمدة **غير قابلة للتحقيق** بأي صفحة App Router،
مهما بلغ تقشّف كودنا. الفجوة 10 KB **قبل** أي شيء نكتبه، و«~13KB للمكوّنات
التفاعلية» المخطط لها في docs/07 §3 تجعل الرقم 113 KB.

هذا ليس خطأ تنفيذ يمكن ضبطه — إنه تعارض بين رقمين معتمدين.

### لماذا لم يظهر التعارض قبل الآن

الميزانية كُتبت في Phase 0 على أساس أرضية Next 14 / React 18 (≈75–80 KB gzip).
`react-dom` في React 19 أكبر، وrouter الـ App أكبر. الرقم `90KB` كان معقولاً
حين كُتب، ولم يُقَس مذّاك — وهذا بالضبط سبب اشتراط «الميزانيات مفروضة في CI».

## القرار المقترح

**تُخدَم `/i/{slug}` كـ HTML ثابت مبثوث بلا hydration إطلاقاً،
والسلوكيات التفاعلية سكربت vanilla واحد صغير.**

```
Route Handler  →  renderToReadableStream(<InvitationRenderer …/>)
               →  text/html
               →  صفر React على العميل، صفر RSC payload، صفر hydration
               +  /public/invitation.js   (سكربت تحسين تدريجي واحد)
```

الميزانية المتحققة: **JS = حجم سكربتنا وحده** (بضعة كيلوبايتات)، لا 100 KB + سكربتنا.

### لماذا هذا ليس التفافاً

القرار **يحافظ** على كل ما اعتُمد بدل أن يخفّفه:

| ما اعتُمد | الحالة تحت هذا القرار |
|-----------|------------------------|
| ميزانية ≤ 90KB | ✅ **تُحقَّق بفارق كبير** بدل أن تُرفَع لتناسب الواقع |
| نفس `InvitationRenderer` للمعاينة والنشر (ADR-0004) | ✅ بلا تغيير — نفس المكوّن، نفس اللقطة |
| السقوط الآمن: قسم يفشل ⇒ الصفحة تبقى (M3) | ✅ محفوظ — `renderToReadableStream` وحده يدعم حدود الخطأ أثناء SSR |
| CSP بلا `unsafe-inline` (docs/12 §4) | ✅ **أسهل** — لا سكربتات hydration inline تحتاج nonce |
| Server Component افتراضياً (docs/07 §3) | ✅ أقصى صورة منه: **كل شيء** يُعرض على الخادم |
| التخزين المؤقت على الحافة (ADR-0005) | ✅ HTML ثابت خالص = مرشّح CDN مثالي |

والأهم: **التصميم القائم يفترض هذا أصلاً.** الـ Renderer المنجَز في M3 لا يصدّر
أي مكوّن عميل — يصدّر HTML ثابتاً يحمل خطّافات بيانات:

```
data-countdown-target   data-countdown-timezone
data-music-toggle       data-music-audio
data-rsvp-form          data-max-party-size
```

وتعليق M3 على قسم العد التنازلي يقول حرفياً:
> *«الحساب سلوك عميل، يُربط في M6 ويُصحَّح مقابل وقت الخادم.»*

أي أن الطبقة التي تحتاج hydration **غير موجودة** في الصفحة العامة. دفع 100 KB
من React لتشغيل ست سلوكيات مجموعها ~4 KB هو ما يحتاج تبريراً، لا العكس.

### السلوكيات وتكلفتها

| السلوك | الآلية |
|--------|--------|
| العد التنازلي | `data-countdown-target` + انحراف ساعة محسوب مقابل ختم زمني من الخادم |
| مشغّل الموسيقى | نقرة صريحة على `[data-music-toggle]` — لا تشغيل تلقائي أبداً |
| معرض بصندوق ضوئي | مفوَّض من مستمع واحد، يُبنى عند أول نقرة |
| المشاركة | `navigator.share` مع احتياطي نسخ الرابط |
| كشف التمرير | `IntersectionObserver`، ويُتخطّى عند `prefers-reduced-motion` |
| نموذج RSVP (M7) | نموذج HTML أصلي — يعمل بلا JS، والسكربت يحسّنه فقط |

### الكلفة الصريحة

| الكلفة | التقييم |
|--------|---------|
| لا يمكن استخدام `generateMetadata` / `opengraph-image.tsx` | الترويسة تُبنى يدوياً — وهذا يعطي تحكماً دقيقاً في CSP و nonce وCache-Control على أي حال |
| لا Client Components في هذا المسار | مقصود؛ أي حاجة مستقبلية لها تعني إعادة فتح هذا الـ ADR لا الالتفاف عليه |
| كودنا التفاعلي vanilla لا React | ~4 KB بلا إطار مقابل 100 KB معه؛ ومختبَر عبر E2E على متصفح حقيقي |
| مسار عرض ثانٍ في التطبيق | **حقيقي.** المخفِّف: الـ Renderer واحد، والمختلف هو غلاف الاستجابة فقط |

## البدائل المرفوضة

| البديل | لماذا |
|--------|-------|
| **رفع الميزانية إلى ~115KB** | يمكن فعله بسطر واحد، ويجعل الرقم يتبع التنفيذ بدل أن يقيّده. الميزانية موجودة لأن الجمهور المستهدف على 4G بطيئة وأجهزة متوسطة — الواقع الذي بررها لم يتغيّر |
| Pages Router لهذا المسار وحده | أرضية أصغر لكنها ليست صفراً، وخلط الموجّهَين في تطبيق واحد كلفة صيانة دائمة مقابل مكسب جزئي |
| قبول 100 KB والاكتفاء بـ Lighthouse | Lighthouse قد يمرّ على 4G محاكاة بينما 100 KB تظل 100 KB على جهاز حقيقي في اتصال ضعيف. المقياس الميداني (p75 LCP) هو ما يهم |
| `renderToStaticMarkup` بدل البثّ | **يكسر ثابتاً من M3:** حدود الخطأ لا تعمل في هذا الـ API، فقسم واحد يرمي استثناءً يُسقط الصفحة كاملة — وهو الفشل الذي لا يُحتمل ليلة عرس |

## العواقب

### إيجابية
- الصفحة العامة تصبح **أسرع بنيوياً**، لا مضبوطة لتبدو سريعة.
- CSP أصرم بطبيعته: لا سكربت inline يحتاج استثناء.
- الصفحة تعمل **بلا JavaScript إطلاقاً** — يبقى النص والصور والروابط والنموذج.
- LCP لا ينتظر أي تحميل أو تنفيذ سكربت.

### سلبية
- غلاف عرض ثانٍ يجب أن يبقى متوافقاً مع الأول — مخفَّف باشتراك الـ Renderer نفسه واختبار يمنع تسرّب أي مكوّن عميل إلى هذا المسار.
- أي ميزة عامة مستقبلية تحتاج حالة React تصطدم بهذا القرار عمداً.

## المطلوب من المالك

**قرار صريح بين خيارين، لا أكثر:**

1. **اعتماد هذا الـ ADR** — تبقى الميزانية 90KB كما اعتُمدت، وتُحقَّق فعلاً.
2. **رفض واعتماد رفع الميزانية** إلى ما تسمح به أرضية App Router (~115KB مبدئياً)
   وتعديل PRD §4.1 و docs/07 §10 تبعاً لذلك.

نُفِّذ M6 على أساس الخيار (1) لأنه **الوحيد الذي يحترم رقماً معتمداً بالفعل**؛
والرجوع إلى (2) تغيير غلاف الاستجابة في مسار واحد، لا إعادة بناء.
