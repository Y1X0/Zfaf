# ADR-0005 — النشر عبر Immutable Snapshot بدل القراءة الحية

**الحالة:** ✅ Accepted · **اقتُرح:** 2026-08-16 · **اعتُمد:** 2026-08-16

## السياق

الدعوة المنشورة تُقرأ مئات الآلاف من المرات، ويُشارَك رابطها مع 250+ ضيفاً على WhatsApp.
في الوقت نفسه، صاحب الدعوة يواصل التحرير، ونحن نواصل تحديث القوالب.

**السيناريو الكابوسي:** المستخدم يفتح دعوته ليصلح خطأً مطبعياً، فيرى 200 ضيف — في تلك اللحظة —
دعوة نصف محرّرة. أو: نحدّث قالباً فتنكسر دعوة عرس الليلة.

## القرار

**فصل كامل بين مستند المسودة والنسخة المنشورة.**

```
invitations.draft_document (JSONB)          ← يتغيّر مع كل تعديل
              │
              │  publish()  →  resolveDocument()
              ▼
invitation_versions.published_document      ← IMMUTABLE، مكتفٍ ذاتياً
              ▲
invitations.published_version_id ───────────┘
```

الصفحة العامة تقرأ **الـ snapshot فقط**، ولا تلمس المسودة ولا القالب الحي ولا جداول الوسائط.

## البدائل المرفوضة

| البديل | لماذا رُفض |
|--------|------------|
| قراءة حية من المسودة | التعديلات تظهر فوراً للضيوف — كارثة تجربة |
| علم `is_published` فقط | لا يحل مشكلة تحديث القوالب ولا حذف الوسائط |
| Copy-on-write بلا نسخ | لا تراجع، ولا سجل، ولا تدقيق |
| نسخ كاملة لكل حفظ | تضخم هائل في التخزين بلا فائدة |

## العواقب

### إيجابية

| الفائدة | التفصيل |
|---------|---------|
| **أمان التحرير** | التعديل بعد النشر لا يظهر حتى «نشر التحديث» الصريح |
| **استقرار القوالب** | الدعوة مثبّتة على `templateVersion` — تحديث القالب لا يمسّها |
| **حماية الوسائط** | الـ snapshot يحمل مراجع محمية؛ حذف صورة مستخدمة مرفوض |
| **تراجع فوري** | `published_version_id` يعود لنسخة سابقة في استعلام واحد |
| **أداء قراءة ممتاز** | استعلام واحد بمفتاح، بلا JOINs ولا حلّ علاقات |
| **قابلية تخزين مؤقت مثالية** | المحتوى لا يتغير إلا بنشر صريح ⇒ إبطال دقيق بـ Cache-Tag |
| **سجل تدقيق** | من نشر ماذا ومتى |

### سلبية
- تخزين إضافي → مخفَّف بحد 20 نسخة لكل دعوة + تنظيف دوري.
- خطوة نشر صريحة (مفهوم إضافي للمستخدم) → مخفَّف بشريط واضح: «لديك تعديلات غير منشورة».
- منطق `resolveDocument` يجب أن يكون شاملاً — أي مرجع غير محلول يصبح رابطاً مكسوراً دائماً.
  → مخفَّف باختبارات تحقق صارمة على الـ snapshot قبل الالتزام.

## تفاصيل التنفيذ

```typescript
function resolveDocument(draft, manifest, mediaMap): PublishedDocument {
  return {
    schemaVersion: 1,
    templateKey: manifest.key,
    templateVersion: manifest.version,
    theme: resolveTheme(manifest.theme, draft.themeOverrides),  // ثيم كامل محلول
    sections: draft.sections.filter(s => s.enabled).sort(byOrder),
    content: {
      ...draft.content,
      media: resolveMediaUrls(draft.content.media, mediaMap),   // روابط مطلقة
      events: resolveEvents(draft.content.events),
    },
    publishedAt: clock.now().toISOString(),
  };
}
```

**خاصية إلزامية:** الـ snapshot **مكتفٍ ذاتياً بالكامل**. عرضه يجب ألا يتطلب أي بحث إضافي
في قاعدة البيانات. هذا ما يجعل استعلاماً واحداً كافياً لأهم مسار في النظام.

## علاقة بـ CQRS

هذا **أخذ الفكرة المفيدة من CQRS بلا بنيته الثقيلة**:
نموذج كتابة غني (draft + قواعد + تحقق) ونموذج قراءة مسطّح ومحسّن (snapshot).
بلا event sourcing، بلا قواعد بيانات منفصلة، بلا اتساق نهائي معقّد.
