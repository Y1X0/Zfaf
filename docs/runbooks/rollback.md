# Runbook — التراجع عن نشرة

**الشدة:** P0 حين تكون النشرة سبب الحادث · **التنبيه:** `publish_failing`

**القاعدة:** تراجَع أولاً، وافهم بعد ذلك. الفهم يمكن أن يحدث والموقع يعمل.

## متى يكون هذا هو الإجراء

- بدأ الحادث خلال دقائق من نشرة.
- `error_rate_severe` أو `public_invitations_failing` يشتعل، والصحة العميقة سليمة.
- انحدار وظيفي واضح لا يفسّره تابع خارجي.

## 1. تراجع الكود

```bash
# ما الذي نُشر، ومتى؟
git log --oneline -10 origin/main

# أعِد آخر إصدار معروف بصلاحه
git revert --no-edit $BAD_SHA && git push origin main
```

لا `git push --force` على `main`. التراجع نشرة إلى الأمام لا محو للتاريخ —
والتاريخ هو ما ستقرؤه في مراجعة الحادث.

## 2. وماذا عن الـ migrations؟

**التراجع عن الكود لا يتراجع عن قاعدة البيانات، وهذا مقصود.**

docs/14 §5 يفرض نمط الخطوتين لهذا السبب بالضبط: كل migration متوافقة مع
الإصدار السابق من الكود. أي أن الكود القديم يعمل على المخطط الجديد — فالتراجع
عن الكود وحده آمن، ولا حاجة لعكس المخطط تحت الضغط.

إن كانت migration **غير** متوافقة قد نُشرت، فهذه حالة مختلفة تماماً:
[migration-failed.md](migration-failed.md).

## 3. الدعوات المنشورة لا تتأثر

نقطة تهدئة تستحق أن تُقال أثناء الحادث: كل دعوة منشورة تُعرَض من **لقطتها**
غير القابلة للتعديل (`invitation_versions`، ADR-0005)، لا من كود العرض الحالي
ولا من مسودة المستخدم. نشرة سيئة تكسر البنّاء ولوحة التحكم؛ الدعوة المرسَلة
ليلة أمس تبقى كما كانت.

## 4. تراجع نشر دعوة واحدة

مختلف تماماً عن ما سبق، ولا علاقة له بالنشر البرمجي: صاحب الدعوة نشر نسخة
خاطئة ويريد السابقة.

`/dashboard/invitations/{id}` ← «الإصدارات» ← «استرجاع». يُنشئ إصداراً جديداً
من محتوى القديم؛ لا يُعدَّل أي صف قديم ولا يُحذف (المُشغِّل يمنع ذلك أصلاً).

## بعد التراجع

- أكّد الخضرة: `/api/health/deep`، ثم `/i/{slug}` معروف، ثم إرسال RSVP تجريبي.
- **اكتب الاختبار الذي كان سيمنعه** قبل إعادة النشر. النشرة الثانية بلا اختبار
  هي النشرة الأولى مرة أخرى.

## آخر تمرين

**لم يُنفَّذ على staging** — بوابة إطلاق مفتوحة صراحةً (docs/14 §15).
